# SGME 架构设计 0.3 审查意见

> 审查对象：`docs/design/SGME-架构设计-0.3.md`（2026-08-03）
> 审查日期：2026-08-03
> 总体评价：标签化记忆池 + 模板查询的方向正确，比固定结构体画像更贴合追加式记忆、实时视图的本质。但存在 1 处数据流硬伤（记忆池输入方三处矛盾）、2 处语义混乱（time_velocity、开放问题编号），以及若干语义缺口与优化点，建议在最小闭环动工前修正。

---

## 一、必须修正（矛盾 / 错误）

### 1. 记忆池的输入方：§8 与 §3/§9.1 三方矛盾

全文对「记忆池（Memory DB）的数据从哪来」有三种说法：

- §8 写入路径：原始 → 精炼知识点 → 标签化记忆池（记忆池来自精炼层二次提炼）
- §8 分层映射：L1 原子事实 + L2 场景 ≈ Wiki DB 精炼层（照此记忆池没有写入方）
- §3 + §9.1：L1 直接产出标签化记忆（进 Memory DB），L2 场景才是精炼层标准形态

正确链条（与 §3/§9.1 一致）：

```text
L0 原始(Wiki 原始层) → L1 标签化记忆(Memory DB) → L1.5 池内裁决
    → L2 场景叙事(Wiki 精炼层) → 模板查询画像（零 LLM）
```

**建议**：修订 §8 写入路径图与分层映射，统一为「L1 产记忆、L2 产场景、画像 = 记忆池查询」。

### 2. time_velocity 术语与概念双重混乱

- 枚举不一致：§8.1/§9.1 定义 static/dynamic 两值，§8.2 模板示例却写 `[slow, dynamic]`（slow 全文无定义）
- 概念混淆：§8.1 称 time_velocity「可作为模板查询中的可选时间窗过滤条件」——它是**变更频率**元属性，不是**时间窗**（按 updated_at 的新旧过滤）。模板「今日节奏」想表达的其实是「最近更新」，用 time_velocity 过滤语义错位

**建议**：统一枚举 static/dynamic；模板查询显式引入 `time_window`（如 updated_at > 7 天前）字段；time_velocity 仅作排序提示或频率相关过滤，不冒充时间窗。

### 3. §14 开放问题编号混乱

- 已解决 #11（维度标签扩展性）与待定型 #11（通知适配器优先级）**编号冲突**
- 待定型注释引用「#12/#13/#14/#15/#17 已闭环」，但已解决列表实际是 #11–#15，且 **#17 不存在**（跨机拓扑已重编为 #15）

**建议**：待定型项重排为 16/17/18，注释与已解决列表编号对齐。

## 二、建议补充（语义缺口）

### 4. 模板查询引擎的 FTS5/向量描述错位

§8.2 查询引擎称「标签过滤 + FTS5 + 向量搜索」，但模板 query 只有结构化字段（dimensions / priority / sort / limit），无搜索词——FTS5/向量在模板查询中无从用起。它们是 /search（Tier 2/3）的能力。

**建议**：§8.2 明确模板查询 = 纯结构化 SQL（标签过滤 + priority/updated_at 排序 + limit）；FTS5 + 向量仅用于 /search 接口，避免实现者造无用索引与流程。

### 5. Tier 0 摘要生命周期缺口

- 生成频率「每天 / 每次对话后」二选一未定（本地 LLM 无成本约束，但频度影响摘要时效）
- 生成失败 / 过期时的注入降级路径未定义——摘要不可用时 Tier 0 应降级为静态维度模板查询直出
- 摘要生成走提炼管线还是独立 LLM 任务未指明

### 6. L1 维度标注治理缺失

- LLM 输出中文维度名（"技术栈"）与存储 id 之间无归一化映射（别名表：技术栈 / 技术选型 / 踩坑 → 同一 id）
- 未知标签策略未定义：建议「丢弃 + 告警」，不自动注册（防标签爆炸）
- 维度注册表变更 → L1 提示词需动态注入当前维度清单，与开放问题 18（提示词版本管理）的联动机制未提

### 7. freshness 只列待办、无设计决策

动态维度（状态 / 关注 / 待办）陈旧记忆污染注入，是 v0.3 的核心质量风险，不应只挂在 §19 待办③。

**建议**：§8.2 固化默认排序语义——静态维度默认 priority DESC，动态维度默认 updated_at DESC + 可选 TTL/expiry 字段（记忆级）。

### 8. L1.5 候选池规模失控（用户修订：不设上限、分批提炼）

OR 预过滤 + 高基数维度（项目 / 技术栈 可能数百条）→ 候选池可能超出单次 LLM 调用上下文预算（本地默认 64K）。

**原建议**：候选池设上限，按 priority DESC + 语义 top-k 采样（如 30 条）+ 分片。

**用户修订（2026-08-03 采纳）**：候选池**不设上限、全量保留**——截断会漏掉潜在冲突对（重复事实入库），与 OR「宁宽勿漏」初衷矛盾；调用次数不是瓶颈，**单次上下文才是硬限制**。改为：送 LLM 前按**当前配置模型上下文预算**（预算 = 模型窗口 − 输出预留 − 提示词开销，随模型动态变化）**分批送入**，批内 priority DESC，**同一新记忆只进一批**（防跨批矛盾提炼），批间无依赖可并行，超大批数产 `anomaly_warn`（可观测性而非截断）。已落入 v0.4 §9.1 / §14 #20。

> 术语说明（2026-08-03 二轮）：「裁决」统一为「冲突提炼」——store/skip/update/merge 四动作是提炼规则（§9.1 Rules）的一部分，不引入生造词。

## 三、优化建议

### 9. 原始层无限增长 vs 全量快照

「原始层不主动淘汰」+ 每日 SQLite 全量快照：Hermes 会话全量入库，年增 GB 级，快照随之膨胀。

**建议**：冷归档窗口（>90 天压缩 / 只读）+ 快照分层（日增量 / 周全量 / 月归档）。

### 10. SCSM 长时间离线信号重放

push 断线重连若全量补拉会信号风暴。

**建议**：重放窗口上限（如 1 小时）+ 同源同类型合并摘要。

### 11. 双画像漂移（Hermes memory ↔ SGME）

§18 只解决 Hermes → SGME 单向同步。SGME 稳定后，Hermes memory 中长期画像条目建议逐步让位 SGME（memory 工具专注即时态），避免两处维护漂移。

### 12. 模板配置校验

- section.dimensions 应 ⊆ 模板 memory_types（配置错误拦截）
- full 模式各 section 的 limit 总量需 ≤ InjectReq.max_tokens 联动预算

### 13. §9.3 落地模型清单

「Flash/Instruct 可行」过于抽象，建议落到当前 LM Studio 实际可用实例（qwythos-9b-claude-mythos-5-1m），并标注 gemma-4-12b-qat 禁用，防后续配置错选。
