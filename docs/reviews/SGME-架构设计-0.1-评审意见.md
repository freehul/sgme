## 一、整体评价

架构质量很高。三进程解耦、双契约对称（MemoryHub / AgentDispatch）、记忆可溯源作为硬约束、Fork 腾讯云底座叠加差异化层——这四个核心决策都站得住。12 条设计原则锁得死，模块边界以「负责 / 不负责」界定的方式清晰且可执行。开放问题从早期 14 条收敛到 4 条，说明讨论质量高。

以下按风险等级排列意见。

## 二、需要在架构阶段考虑的问题

### 🔴 建议锁定（影响模块边界或后续实现结构）

#### 1. SCSM 内部缺乏分层，有膨胀风险

SCSM 当前承载 8 个模块：任务池、触发器引擎、执行编排、自愈、通知、UI 视图、外部事件摄入、Admin 桥。虽然整体作为一个独立进程没有问题，但模块间耦合度未界定。随着桌宠/灵动岛等 UI 扩展加入，SCSM 内部复杂度可能快速增长。

**建议**：SCSM 内部至少分两层——

- **核心层**：任务池 + 触发器引擎 + AgentDispatch + 执行编排 + 自愈
- **扩展层**：UI 视图 + 通知通道 + 外部事件摄入 + Admin 桥

核心层稳定后，扩展层可独立演化（甚至拆出子进程），不影响调度主干。这不需要改架构图，只需在 SCSM 模块描述中注明层级关系。

#### 2. 信号引擎规则的生命周期未定义

§3 说 signal_engine「基于记忆 + 知识 + **规则**产出信号」，但规则由谁写、谁改、存哪里、版本怎么管，均未提及。如果规则硬编码在 SGME 内部，调规则就要重启 SGME，与「可分别重启」原则（原则 1）和「SGME 纯数据不执行」（原则 3）的精神矛盾。

**建议**：明确规则外置（配置文件或规则库），SGME 热加载。规则的 CRUD 归入 MemoryHubAdmin 管辖。这不需要现在定技术方案，但边界要先锁——「规则是数据还是代码」这个归属问题影响后续所有实现决策。

#### 3. 全量提炼缺少重复判定机制

文档 §9.1 定义了四种调度模式（批量 / 会话级 / 每轮触发 / 首接全量），但未提及**重复判定**：当全量提炼跑第二遍时，如何识别已经提炼过的内容并跳过？

- 如果没有去重机制，全量提炼每次都会重复处理已提炼的原始数据，浪费 LLM 调用。
- 增量模式依赖 `last_run` 游标，但游标只能解决「新增数据」的识别，无法解决「旧数据的提炼结果是否仍有效」的问题。

**建议**：在 Refinement 模块职责中补充「**去重/增量判定**」子能力：

- 原始层条目带 `refined_at` 标记，提炼后打标，下次全量跳过已标条目（除非源数据被修改）。
- 或者用内容哈希对比——原始内容未变则跳过。
- 这属于提炼模块的内部机制，不影响模块边界，但应在架构层面声明其存在，避免实现时遗漏。

#### 4. 多 Agent 同时写入 user 级画像字段的并发控制

§3 定义了 Scope 模型：user 级记忆被所有 Agent 共享。但如果两个 Agent 同时更新同一个字段（如 `preferences.communication_style`），谁的写入生效？

当前 §8.1 只说「旧值经 Supersession 归档」，没有定义并发写入时的仲裁策略。

**建议**：在 §8.1 或 §3 的 Scope 描述中补充一句：并发写入时以 **last-write-wins + Supersession 归档旧值** 为默认策略（简单、可溯源）；如果未来需要更复杂的仲裁（如来源权重），可在此基础上扩展。这只需要一句话锁定策略方向，不涉及实现细节。

### 🟡 建议记录（不影响当前架构完整性，后续定型时处理）

#### 5. Memory Mode 的优先级链需显式锁定

§10 说模式可 AI 生成、可用户管理、用户可强制覆盖。文中暗示了优先级顺序（用户强制 > Agent 指定 > 全局默认 > 系统推荐），但没有显式声明为规则。

**建议**：在 §10 末尾加一句优先级声明即可：

> 优先级链：用户强制覆盖 > Agent 每次 Inject 指定 > 用户全局默认 > 系统推荐。冲突时高优先级胜出，不合并。

#### 6. 每轮触发模式的判定粒度

§9.1 说每轮触发「暂使用与全量相同的提炼规则」。经澄清，这里是指规则本身相同（提取什么、如何 Supersession），而非每轮都跑全量提炼。理解纠正后，成本风险大幅降低。

但仍有一个问题：**每轮触发的判定入口是什么？** 即——每轮对话结束后，什么东西决定「这轮对话值得提炼」？

- 如果每轮都无条件触发提炼（只是用同样的规则处理单轮数据），成本仍然偏高。
- 如果有个轻量判定步骤（如「本轮对话是否包含新的事实性信息」），这个判定本身的成本和准确率需要评估。

**建议**：在 §9.1 的「每轮触发」描述中补一句：「具体判定阈值（何种对话内容触发提炼）留待技术实现阶段定义，架构层面仅声明该模式存在。」——这样既不限制实现，又提醒后续需要处理这个问题。

#### 7. 知识库原始层的存储上限与淘汰策略

原始层保留所有原始会话和资料，但文档未提及：

- 容量是否有上限？
- 是否按时间/项目淘汰？
- 还是全量永久保留？

**建议**：在 §8 的知识库描述中补一句：「原始层存储上限与淘汰策略留待技术实现阶段定义；架构层面假设原始层可无限增长（至少在可预见的使用周期内）。」——这避免了实现时才面对存储爆炸问题。
