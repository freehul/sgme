## 三、确认项（文档做得好的地方）

一、**三进程契约解耦**：SGME 纯数据、SCSM 唯一调度、Agent 只做会话智能；MemoryHub 与 AgentDispatch 对称设计，接口家族对称性表述清晰，是本方案最大亮点。

二、**记忆可溯源内核**：双库 + 溯源三元组 + Supersession 归档，对齐 Zep 双时态 / Mem0 时间线 / A-MEM / Generative Agents，论证有据；"Supersession 融合失效归档 + 时间线不覆盖"的定位准确。

三、**渐进式注入零-LLM**：Tier 0/1/2 与 8-02 已定角色系统 v2（domain 过滤器 + layer 阈值）完全一致，注入路径 <100ms 约束合理，是工程上最稳的设计。

四、**评审补充机制成熟**：并发写仲裁（last-write-wins + 归档）、规则归属（数据非代码）、模式优先级链（用户强制 > Agent > 全局默认 > 系统推荐）等 8-03 评审补充均把「实现时易踩的坑」提前锁死，闭环速度快。

五、**降级链抽象正确**：`call_with_fallback()` 主→备→本地→规则，提炼与模型解耦，符合提纯铁律（Flash/Instruct 可行，Pro/Reasoner 不可——具体模型选择留实现阶段即可）。

## 四、高优先级问题（Fork 前必须解决）

**一、🔴 技术栈矛盾：Python 决策 vs TS 底座——文档最大的未决矛盾**
　已确认决策②锁死「技术栈 Python，旧代码 166 文件/68 测试可复用」。但底座是 Node.js/TypeScript：存储 + L0→L3 蒸馏 + BM25/向量/RRF 检索 + Hermes 适配全部在底座内，这些恰是旧代码最值钱的部分（engine/*、storage/*、search/*）。Fork 后旧代码只剩差异化层（signal_engine / SCSM / 注入）可用，166 文件的复用价值缩水大半，且长期维护变成双语言。
　**这不是 Fork 方案的错，但必须显式决策**：①接受双栈（TS 底座 + Python 差异层，推荐，成本最低）；②Fork 仅作参考实现，核心仍用 Python 自研（回到原点，违背 8-03 决议）；③底座容器化，差异层 Python 经 HTTP 调用（与 ① 等价但隔离更干净）。§14-13 只写「待确认底座技术栈」是不够的——事实是「Python 决策已被 8-03 决议实质推翻」，需要在文档里显式记录这一变更及其代价。

**二、🔴 底座安全漏洞（Issue #672，2026-08-01 报出，未修复）**
　公开 SECURITY ADVISORY：MemoryProxy 与 MemoryKnowledge 存在**未认证 Admin 端点、认证绕过、SSRF**。文档 §6 把安全押在「契约层 API Key + 传输层 Gateway 令牌 + localhost 旁路」三层模型上，但底座自带认证绕过意味着地基有洞——攻击者可能绕过 Gateway 令牌直达数据层。
　**必须**：Fork 后立即修（或隔离）该漏洞再部署；架构文档补一节「底座安全基线清单」（哪些已知 CVE/issue 在 Fork 时必须打补丁）；SSRF 在单机场景威胁降低但 NAS 跨机部署时真实存在。

**三、🔴 提炼管线静默停摆风险（Issue #549，2026-07-22，未修复）**
　底座 L1 提炼链路有健壮性缺陷：**静默停摆数天，L0 捕获一切正常，用户无感知**。SGME 提炼管线若直接复用，此风险继承——而提炼是「写-管-读」核心，停摆意味着画像冻结、关怀失明。
　**必须**：架构层加「提炼健康可观测性」——`refined_at` 游标推进率监控、提炼水位看板、异常即发 `anomaly_warn` 信号（正好复用 §11.1 信号字典）。§9 的「失败可重试/补偿」只覆盖单次失败，不覆盖「静默不跑」。

**四、🔴 Windows 部署可行性（Issue #655，2026-07-31，未修复）**
　`start-all.sh` 硬编码 `/usr/bin/curl`，Windows Git Bash 下初始化直接失败（HTTP=000）。**用户主环境正是 Windows**，且计划 NAS 部署。Fork 前必须验证：本机 Windows 跑通最小闭环（capture → L1 提炼 → search），或确定 Docker/WSL 路径。此条不解决，§1「本机 / NAS 常驻」直接落空。

**五、🔴 备份与恢复缺失——架构文档必须补的章节**
　记忆是最高价值资产（铁律：原件永不删），但全文无备份设计。双库 + 原始层「可无限增长」假设下，一旦磁盘损坏或误删，Supersession 溯源链整体断根。架构层面必须定义：备份周期与快照策略、恢复演练、备份本身带版本（与溯源链对齐）。此项与功能无关，但与「记忆可溯源」内核同等重要。

## 五、中优先级问题（定型前解决）

**六、🟡 SCSM 存在性论证缺失**
　Hermes 已有 cron / 进程管理 / 通知 / hooks。SCSM 的触发器引擎、任务池、通知通道与这些高度重叠。单用户场景多一套常驻调度器是显著复杂度，文档没回答「为什么不用 Hermes cron」。理由其实成立（跨 Agent 统一调度、UI 可视化、SGME 自愈托管、Agent 无关），但需要显式写一节「SCSM vs Agent 内置调度器边界」，否则实现时每个模块都要重答这个问题。

**七、🟡 Hermes 侧记忆接入拓扑未定**
　底座插件占 Hermes 唯一 memory provider 槽位（`memory.provider: memory_tencentdb`），差异化层（Memory Mode / signal / 双库溯源）走 MemoryHub（HTTP）。两个入口并存，谁优先、如何防双写不一致、Hermes 内建 memory 工具被替换后的行为变化（tools 名变为 tdai_* 前缀），文档没讲。需要一张「Hermes 记忆接入拓扑」图：provider 直连 vs MemoryHub 适配器的分工。

**八、🟡 信号反馈循环无抑制设计**
　`memory_updated` 信号 → SCSM 触发器 → 唤醒 Agent → Agent 写记忆 → 提炼 → 又一条 `memory_updated`。§13.5 有信号 id 幂等（防重复触发），但没有「因自身处理结果再触发自身」的环抑制。建议：信号带 source 标记 + SCSM 侧同源抑制窗口（如 30 分钟内同源同类型信号合并）。

**九、🟡 全量批量提炼成本无预算**
　「首接全量（Hermes 会话库全量）」的 token 成本没估算。用户会话库永久保留、体量可观，全量提炼一次可能消耗数月模型订阅预算。llm 模块只提「统一配额与审计」无数字。建议架构层给上限策略：全量提炼分批限速（如每天 N 会话）、成本熔断阈值、以及提炼默认走哪条降级链（本地小模型 vs 云端）。

**十、🟡 单用户下 ACL 字段降级未说清**
　文档声明「不设 tenant/user 维度、agent_id 仅溯源不隔离」，但 §6 又说底座数据层 ACL（private/team/restricted/agent）「同向对齐」。private/team/restricted 是典型多租户概念，单用户下是死代码或需字段映射。需明确：映射为单一值还是裁剪掉——两处表述存在表面矛盾，建议统一口径。

**十一、🟡 跨机部署的 LLM 可达性**
　SGME 在 NAS、本机 LLM（LM Studio :1014）时，提炼管线从 NAS 出发不可达本机端点。降级链的「哪个进程从哪里访问哪个模型端点」需要一张部署拓扑图，否则跨机部署（§6 已假设此场景）会在 LLM 层卡住。

## 六、低优先级 / 建议

**十二、🟢 注册中心离线降级**：注册表放 SGME 内，与原则 10「SCSM 无 SGME 亦可运行」有张力——SGME 离线时唤醒目标解析可能失败。建议注册表在 SCSM 侧本地缓存/镜像。

**十三、🟢 契约传输默认值**：开放问题 12 建议直接定 HTTP/JSON（与 Gateway :8420 一致）为首版默认，gRPC/消息队列不做首版，降低落地门槛。

**十四、🟢 术语表**：「司辰 SCSM」与 Hermes cron 的语义区分（调度 vs 定时）建议在文档补一句，避免团队沟通歧义。

## 七、结论与建议行动

**总体**：架构设计质量高，Fork 决策方向正确且已核实成立。但「Fork 底座」不是免费的——它把腾讯云项目的已知缺陷（安全、提炼健壮性、Windows 部署）一起搬了进来。

**建议行动顺序**：

一、**先做底座体检（1-2 天）**：本机 Windows 跑通 v2.0.0-beta.1 最小闭环（部署 → capture 一条会话 → L1 提炼 → 检索验证），同时验证 Issue #655 是否影响、确认 #549 停摆现象能否复现。

二、**修或隔离安全漏洞**：Fork 仓库里先打 #672 补丁（或确认上游修复版本），写进「底座安全基线清单」。

三、**补文档两处硬伤**：①技术栈矛盾显式决策（建议双栈：TS 底座 + Python 差异层）；②新增「备份与恢复」章节。

四、**补可观测性**：提炼水位监控 + `anomaly_warn` 上报纳入 §9，作为架构级要求而非实现细节。

五、**再评审**：以上四项闭环后，v0.2 评审重点看 §14 开放问题 10-13 与「Hermes 记忆接入拓扑」图。
