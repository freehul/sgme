# SGME v0.7 实施任务清单（架构师交付：影响面分析 + 四阶段任务分解）

> **唯一架构依据**：`docs/design/SGME-架构设计-0.7.md`
> **配套方案**：`docs/plans/operations-layer-extraction.md`、`docs/plans/architecture-renovation-v0.7.md`
> **项目根**：`D:\Projects\SGME`（Windows / git-bash）
> **性质**：仅设计与任务分解，不含业务实现代码
> **硬约束**（来自 AGENTS.md + v0.7 设计）：
> 1. `engine/`、`profile/`、`prompts/`、`signal/`、`raw/` 业务逻辑**只改 import / 改 conn 来源，不改逻辑**
> 2. API 契约（JSON schema）**不变**；HTTP 路由与 MCP 工具行为等价
> 3. 所有 DB 操作**必须**经由 `data/`（原 storage/）层；`server/routes_*` 与 `mcp_server` **禁止裸 SQL**（backup 裸连接为唯一豁免，须加注释）
> 4. `operations/` 是 HTTP/MCP **唯一**操作入口；入口层只做协议翻译，且入口层之间**互不 import**
> 5. 依赖方向铁律：`adapters → server/mcp_server → operations → engine/refinery → data/llm/profile/prompts → config/log`

### 0.3 关键架构决策（已定，工程师照做）

| # | 决策 | 内容 |
|---|------|------|
| D1 | **三库连接接口** | `db.py` 暴露 `get_memory_conn()` / `get_session_conn()` / `get_wiki_conn()`；`init_databases()` 改为返回三库三元组 `(mem_conn, session_conn, wiki_conn)`。旧 `connect_memory/connect_wiki` 保留为别名或直接改名。 |

| D5 | **旧表保留策略** | 迁移脚本**复制**数据到新库，**保留**旧 `wiki.db` 作为归档（不 DROP）。代码侧 `connect_wiki()` 在启用时仅建 `wiki_pages`/`wiki_links`，不再建 raw_files/scenes。旧 wiki.db 如需清理由运维手动 `wiki.db.legacy` 改名。 |

## 2. 阶段 1：数据库重组（破坏性变更）

**目标**：双库 → 三库；raw_files/scenes 系列搬家；新建 refine_cursor / memory_stats。
**顺序**：先 `migrations/` + 脚本 → 再 `db.py` 接口 → 再 data 层 DAO → 再 engine/search → 最后 server/backup/mcp/adapters。

### 2.1 `migrations/` 目录规范（放项目根，不进 `sgme/` 包）

> **边界铁律（用户原话「migrations/ 目录」）**：迁移脚本是一次性运维资产，放在 `sgme/` 包**之外**的项目根 `migrations/`。
> 阶段 2 的 `git mv sgme/storage sgme/data` 包重命名对它**零影响**——只需改一行 `from sgme.storage.db import ...`。
> 它通过 `sgme.storage.db` 拿连接，不写裸 SQL 之外的业务逻辑，不违反「`data/`（原 storage）是唯一数据库操作层」。

#### 2.1.1 新旧两套迁移机制的边界（B 批决策）

| 机制 | 职责边界 | 触发时机 | 落点 |
|------|----------|----------|------|
| **db.py「连接即迁移」**（`*_DDL` + `_ensure_schema` + `_migrate_*`） | 管**表结构就绪**：每次 `connect_*` 自动建表 / 补列 / 轻量迁移。含新建 `SESSION_DDL`、`MEMORY_DDL` 追加的 scenes 系列五表（**scenes_fts 虚拟表 + 3 个同步触发器不进 db.py**，由 search 层 `init_scenes_fts` 负责，见 B2）、`WIKI_DDL` 收缩（见 §2.5，wiki_fts 同理不进 db.py）。 | 每次连接自动执行 | `sgme/storage/db.py`（阶段 2 后为 `sgme/data/db.py`） |
| **`migrations/`（一次性脚本）** | 管**存量数据搬家**：跨库搬运、FTS rebuild、清理旧物（删 `sgme.db`）。**不建新表、不补列**（那归 db.py）。 | 仅 v0.7 升级时 `run_all` 跑一次，可重入 | 项目根 `migrations/` |

> 关键原则：**新建/改造表结构一律写进 db.py 的 `*_DDL`**，由 `_ensure_schema` 在 connect 时落地；`migrations/` 只负责把旧 `wiki.db` 里的存量行搬进新库、重建 `scenes_fts`、删 `sgme.db`。二者职责不重叠，互不越界。
> **FTS 虚拟表的归属铁律（B2）**：`scenes_fts` 与 `wiki_fts` 这两个 FTS5 虚拟表**都不写进 db.py 的 `*_DDL`**——它们由对应的 search 层 `init_*` 函数在 connect 之后创建（scenes_fts 由 `sgme/search/__init__.py:init_scenes_fts`；wiki_fts 由阶段 3 wiki 模块的 search 层负责）。db.py 只管普通列的存在（幂等 ALTER/建表），分词回填 + FTS 建索引归 search 侧。

```
migrations/
├── __init__.py            # 导出 run_all(data_dir, cfg)
├── _registry.py           # 版本注册表：有序迁移函数列表 + applied 标记（登记 0001）
├── 0001_split_three_dbs.py  # 存量数据搬家：迁移前备份 → 跨库搬运 → scenes_fts rebuild → 删 sgme.db（可重入，B5）
└── _move_data.py          # 跨库搬运实现（Python 读写，D2；列名全展开见 §2.3），被 0001 调用
```

**规范**：
- `0001_split_three_dbs.py` 导出 `def up(conn_dict: dict) -> None`，幂等（搬运用 `INSERT OR IGNORE`；删 `sgme.db` 前先 `verify_integrity()` 通过）。
- 只做 DDL 之外的**数据**搬运 + 备份 + 清理；**不创建任何新表/新列**（那归 db.py 的 `*_DDL`）。
- `schema_versions` 表**每个库各有一份**（memory/session/wiki 各自登记），版本号随各自库演进（见 §2.5.1 SCHEMA_VERSION 决策）。
- `run_all(data_dir, cfg)`：先 `connect_*` 建好三库新表（db.py 负责）→ 再执行未登记版本（0001 搬运）→ 写 `schema_versions`。
- 禁止在迁移中写业务逻辑；备份**复用 `backup/manager.py` 的 `create_snapshot()` / `verify_integrity()``**，**勿新写备份逻辑**（见 §2.7）。
- **阶段 1 的所有改动都留在 `sgme/storage/` 内原地完成**（含新建的 3 个 DAO），路径一律 `storage/db.py`、`storage/session_dao.py`、`storage/scene_dao.py`、`storage/memory_stats_dao.py`。阶段 2 整体 `git mv storage data` 时这些 DAO 一并搬走，零额外成本。

### 2.2 建表 DDL（节选自 v0.7 §8）

### 2.3 跨库搬运方案（D2：Python 读写，列名全展开）

> **实测事实②（fts_meta 合并无冲突）**：两库 `fts_meta` 同为 `(key TEXT PRIMARY KEY, value TEXT)`；
> memory.db 现存 `('segmenter','jieba-0.42.1')`，wiki.db 现存 `('segmenter_scenes','jieba-0.42.1')`，
> **key 不重叠** → `INSERT OR IGNORE` 直接合并，无需去重。搬完 scenes 并 `init_scenes_fts(mem)` 后，
> memory.db 的 `fts_meta` 将同时含两把 key，互不覆盖。

**scenes_fts 的 rowid 漂移问题（实测事实③）**
真实 DDL：
```sql
CREATE VIRTUAL TABLE scenes_fts USING fts5(
    content_seg, scene_id UNINDEXED,
    content='scenes', content_rowid='rowid');
```
`content_rowid='rowid'` 表示 FTS 索引绑定 `scenes.rowid`。跨库搬运时 rowid 必然漂移，**光拷数据必错**。

**决策：选 (b) 不保 rowid，搬完统一 rebuild。**
- 理由：`scenes_fts` 是外部内容 FTS5，索引本就必须绑定**目标库** `scenes` 的实际 rowid 重建；
  源库 rowid 在目标库无意义（memory.db 已有自有行），显式 `INSERT INTO scenes(rowid,...)` 反而可能触发 rowid 冲突/损坏。
  FTS5 的 `rebuild` 命令会按目标库当前 rowid 重读 `content_seg` 重建索引，确定性且幂等，且已被 `init_scenes_fts` 实现。
- 因此：scenes 表用普通 `INSERT`（让目标库分配新 rowid），`content_seg` 一并拷过去；最后调 `init_scenes_fts(mem_conn)`（内部执行 `INSERT INTO scenes_fts(scenes_fts) VALUES('rebuild')`）重建索引。

**`_move_data.py` 可直抄实现（列名全展开，无省略号；不用 ATTACH，双连接 Python 读写）**
```python
def move(conn_dict):
    src = connect_wiki_legacy()          # 旧 wiki.db 只读连接（sqlite3.connect）
    session = conn_dict["session"]       # 已建好 raw_files / refine_cursor
    mem = conn_dict["memory"]            # 已建好 scenes 系列五表（scenes_fts + 3 触发器由步骤6 init_scenes_fts 创建）

    # 1) raw_files → session.db（普通表，rowid 无意义，直接 INSERT OR IGNORE）
    rows = src.execute(
        "SELECT file_id, path, session_key, agent_id, started_at, ended_at, "
        "refined_at, last_refined_seq, status, size, content_hash FROM raw_files"
    ).fetchall()
    session.executemany(
        "INSERT OR IGNORE INTO raw_files "
        "(file_id, path, session_key, agent_id, started_at, ended_at, "
        "refined_at, last_refined_seq, status, size, content_hash) "
        "VALUES (?,?,?,?,?,?,?,?,?,?,?)", [tuple(r) for r in rows])

    # 2) scenes → memory.db（不保 rowid；content_seg 一并拷，后续 rebuild 重绑 rowid）
    rows = src.execute(
        "SELECT scene_id, title, content, heat, status, created_at, updated_at, "
        "last_memory_added_at, content_seg FROM scenes"
    ).fetchall()
    mem.executemany(
        "INSERT OR IGNORE INTO scenes "
        "(scene_id, title, content, heat, status, created_at, updated_at, "
        "last_memory_added_at, content_seg) VALUES (?,?,?,?,?,?,?,?,?)",
        [tuple(r) for r in rows])

    # 3) scene_vectors → memory.db（普通表，实测为 BLOB 列，无特殊约束）
    rows = src.execute(
        "SELECT scene_id, embedding, model, dims, embedded_at FROM scene_vectors"
    ).fetchall()
    mem.executemany(
        "INSERT OR IGNORE INTO scene_vectors "
        "(scene_id, embedding, model, dims, embedded_at) VALUES (?,?,?,?,?)",
        [tuple(r) for r in rows])

    # 4) scene_memories → memory.db（普通表，PK(scene_id, memory_id)）
    rows = src.execute("SELECT scene_id, memory_id FROM scene_memories").fetchall()
    mem.executemany(
        "INSERT OR IGNORE INTO scene_memories (scene_id, memory_id) VALUES (?,?)",
        [tuple(r) for r in rows])

    # 5) scene_versions → memory.db（普通表，PK version_id）
    rows = src.execute(
        "SELECT version_id, scene_id, content, version_at, reason FROM scene_versions"
    ).fetchall()
    mem.executemany(
        "INSERT OR IGNORE INTO scene_versions "
        "(version_id, scene_id, content, version_at, reason) VALUES (?,?,?,?,?)",
        [tuple(r) for r in rows])

    # 6) scenes_fts 重建（绑定目标库新 rowid）
    #    关键：init_scenes_fts(mem) 一次性完成【建 scenes_fts 虚拟表 + 建 scenes_ai/ad/au 三触发器 + 回填 content_seg + rebuild】，
    #    函数体逻辑一行不改（仅把调用处连接参数 wiki_conn → mem_conn）。
    #    必须走 search 层，绝不能把 scenes_fts/触发器写进 db.py 的 MEMORY_DDL（见 B2 架构冲突修正）。
    from sgme.search import init_scenes_fts
    init_scenes_fts(mem)

    session.commit(); mem.commit()
```

**不采用 ATTACH 的理由**：外部内容 FTS5（`content='scenes'`）在 ATTACH 跨库时触发器不自动同步到目标库；且上述 rowid 漂移需显式处理。Python 双连接读写方案最稳，可重入。

#### 2.5.1 SCHEMA_VERSION 决策（B 批待回答项）

**决策：session.db 沿用同一全局 `SCHEMA_VERSION` 常量登记 `session_v1`**（即整数版本号复用 `SCHEMA_VERSION`，但 `schema_versions` 表以 `session_v1` 为独立行登记，与 `memory_v4` / `wiki_v4` 互不覆盖）。

理由：
1. `SCHEMA_VERSION = 4` 是「代码当前期望的 schema 整数版本」单一事实源；三库共用一个整数版本更直观，避免三个独立计数器失同步、漏升。
2. 演进解耦通过 **label 维度**实现：`schema_versions` 表每个库各一份，登记键为 `{db}_v{ver}`（`memory_v4` / `wiki_v4` / `session_v1`），整数相同但 label 不同 → 永不互相覆盖；各库可独立追加自己的迁移历史（如 session 后续单独演进只需追加 `session_v2` 行）。
3. **不采用「三库各自独立整数序列」**：会增加三套计数器维护成本，且跨库版本号无统一锚点，排查「代码期望 vs 库现状」更费力；label 已提供足够隔离，无需再分整数序列。

> 结论：保留全局 `SCHEMA_VERSION`；新增 `connect_session()` 调 `_ensure_schema(conn, SESSION_DDL, SCHEMA_VERSION, "session_v1")`。
