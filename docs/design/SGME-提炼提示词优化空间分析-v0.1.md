## 一、P0-1：运行时注册表与源文件漂移 13 天（最严重）

> **定性修正（追查 Backlog / 变更记录后）**：这不是"新发现的漂移"，而是
> **B81「维度裁剪」（2026-08-18）的未闭环尾巴**。溯源见 §1.0。

### 1.0 溯源：B81 改了 yaml，漏了 DB

`docs/design/SGME-实施变更记录-v0.9.md` B81（2026-08-18）原文：

> 4. **维度裁剪**（用户定：项目池/待办池为专用落地点）：registry/dimensions.yaml 移除
>    projects/tasks + aliases.yaml 同步清理 + templates（work/coding/full）去 projects/tasks
>    section 与 memory_types + 测试维度引用修正；**存量标签保留**（memory_tags 历史数据不删，
>    仅不再注入/筛选/展示）
>
> **运维影响**：维度移除后存量 projects/tasks 标签不再注入（历史保留）

即 **B81 的预期是明确的**：yaml / aliases / templates / 测试四处都改了，存量不删，
此后不再注入。唯独**漏了生产 db 的 `active` 停用**。

而 Backlog **T-2**（v0.7，已解决）的裁决是：

> **维度注册表 YAML/DB 重启互相覆盖** — 裁决：**YAML=种子，DB=真相**

`DB=真相` 意味着 db 的 `active` 才是运行时权威。于是形成闭环：

```
B81 删 yaml（种子）  →  但 DB 是真相  →  没执行停用  →  裁剪在生产【零生效】
```

代码层面也有呼应——`memory_dao.py:33 upsert_dimension` 注释
`-- active 不在此更新：保留 DB 现值（停用维度重启不复活）`，
正是 `DB=真相` 裁决的实现。设计本身没错，错在**缺配套的停用动作与一致性提醒**。

**实测打脸**：B81 说"不再注入"，但近 7 天仍新打 `projects` **3,862** 条（维度排名第一）。

### 1.1 现象

| 数据源 | 维度数 | 含 projects/tasks？ |
|---|---|---|
| 生产 db `dimension_registry`（运行时，提示词实际读取） | **16** | ✅ **都有，且 `active=1`** |
| `registry/dimensions.yaml`（源文件） | 14 | ❌ 已删除 |

生产 db 实际清单（全部 `active=1`）：
`environment / family / focus / goals / habits / ideas / identity / preferences / projects / skills / social / status / style / tasks / tech_stack / values`

### 1.2 影响面（生产实测）

| 指标 | 数值 |
|---|---|
| `projects` 标签总数 | **13,499**（全库第一大维度） |
| `tasks` 标签总数 | 2,836 |
| **近 7 天**新打 `projects` 标 | **3,862**（近 7 天维度排名**第一**，超过 tech_stack 3,769） |
| 近 7 天新打 `tasks` 标 | 761 |
| 近 7 天新建记忆 | 9,033 |
| → 打标渗透率 | **约 43% 的新记忆带 projects 标** |
| 08-30（昨天）仍新打 | projects 83 / tasks 14 |

**对照三池落点（刺眼）**：

| 池 | 应有 | 实际 |
|---|---|---|
| 项目池 `project_meta` | 项目信息 | **2 行** |
| 待办池 `demands` | 待办事项 | **114 行** |
| 记忆池里带 projects 标的记忆 | — | **13,499 条** |
| 记忆池里带 tasks 标的记忆 | — | 2,836 条 |

即：13,499 条"项目"记忆**永远进不了 project_meta**（三池分流不认这个标签），
成为只增不减的孤儿数据——实测 `projects` 标签记忆归档数 **0 条**（全库归档率 27.6%，
说明这批记忆连冲突合并都不参与，纯堆积）。

### 1.3 根因（代码级，非操作失误那么简单）

`sgme/data/memory_dao.py:33` `upsert_dimension()` 的 upsert 语句里有一行注释：

```sql
ON CONFLICT(id) DO UPDATE SET
  display_name=excluded.display_name, ...
  boundaries=excluded.boundaries
  -- active 不在此更新：保留 DB 现值（停用维度重启不复活）
```

**这是有意为之的设计**：防止 yaml 里误删维度时，重启导致存量数据失效。
但它带来一个必然副作用——**在 yaml 中删除维度 ≠ 在 db 中停用维度**。

停用必须显式调用 `memory_dao.py:129` 的 `set_dimension_active(conn, id, 0)`。

2026-08-18 三池重构（projects/tasks 维度 → `project_meta`/`demands` 专用表）时，
yaml 侧删干净了，**但生产 db 从未执行停用动作** → 13 天来持续污染。

### 1.4 修复建议

1. **止血（一行的事）**：生产 db 执行 `set_dimension_active('projects', 0)` +
   `set_dimension_active('tasks', 0)`。下次提炼起，`{{dimensions}}` 清单自动不再含这两项。
   ⚠️ 注意：停用后**存量标签不会消失**，模板查询若引用 projects 维度会返回空，需先确认无模板引用。
2. **防复发**：加启动一致性校验——yaml 维度集与 db `active=1` 维度集做差集，
   差异非空 → `anomaly_warn` + 启动日志。这类"改了配置没生效"的坑最适合自动化拦截。
3. **存量治理**（工作量大，单独立项）：13,499 条 projects 标签 → 三个去向
   ① 重新打标到 `tech_stack`/`goals` 等有效维度；② 升格进 `project_meta`；③ 软删。
   建议先抽样 200 条人工看分布，再定批量策略（AIXM 清理教训：关键词批量必翻车）。

## 二、P0-2：提示词缺「待办 → demands 池」通道

> **定性修正（追查 Backlog 后，本条应降级）**：B81（2026-08-18）已就此事**拍过板**——
> 「待办主动登记强化：会话中遇到待办主动 `demand_create`」，
> 并记录当时"83 条待办全来自 Backlog 导入，agent 未主动创建"。
> 现生产 `demands` = **114 行**，较 B81 时的 83 条**增长 31 条** →
> 说明机制**是在工作的**，只是基数小、覆盖率有提升空间。
> 因此本条**不是缺陷，是既定设计 + 观察项**，P0 定级偏高，建议降为 P2。

`AGENTS.md` 三池职责写明：

> **待办池**：**由 agent 主动维护（2026-08-18 强化）**：会话中遇到用户要办的事 / 项目要做的任务 /
> 后续待跟进事项，**主动调 `demand_create` 登记**……不要只留在对话里。

但 `prompts/l1_extraction.txt` 全文**没有任何与待办池相关的指引或输出字段**——
它只说提取"用户画像事实、发生的事件、用户给出的指令或偏好"，外加禁止 ideas 打标。

**后果**：待办在提炼链路里没有出口。

- 停用 `tasks` 维度前：待办被打成 `tasks` 标签 → 沉进记忆池（2,836 条）
- 停用 `tasks` 维度后：待办连标签都没有了 → 只能靠 agent 事后主动登记

而 `demands` 表只有 114 行，对比 2,836 条 tasks 记忆，说明**靠 agent 主动登记这条路
覆盖率很低**（agent 会忘、会漏，尤其是跨会话的隐含待办）。

**需要产品决策**（我不替你拍板）：

| 方案 | 做法 | 代价 |
|---|---|---|
| A 维持现状 | 待办由 agent 主动登记，提示词不动 | 覆盖率低，靠人（agent）自律 |
| B 提炼自动抽取 | `l1_extraction` 输出加 `demands: [...]` 字段，落 `demands` 表（搭现有调用顺风车，零新增调用） | 提示词膨胀 + 误报（把"想法"当"待办"） |
| C 折中 | 提炼输出"疑似待办"候选，人工/agent 二次确认后入池 | 多一道确认，但精度可控 |

📌 个人倾向 **C**：待办误报成本高于漏报（漏报用户会再说一遍，误报会污染待办池）。

## 三、P1：质量校准与治理

### P1-1 priority 分数膨胀

生产分布（25,824 条）：

| 区间 | 条数 | 占比 |
|---|---|---|
| 80–100（提示词定义"核心事实"） | 9,698 | **37.6%** |
| 60–79（"一般事实"） | 15,568 | 60.3% |
| <60（提示词要求 <50 丢弃） | 558 | 2.2% |

**问题**：37.6% 的记忆自称"核心事实（身份/家庭/价值观/重要决策）"——明显偏高。
LLM 打分天然向中高分集中（典型分数膨胀）。后果是 `priority DESC` 排序**区分度下降**：
六成记忆挤在 60–79 区间，inject 的 top-N 选择近似随机。

**优化**：提示词补**锚点示例**（few-shot 比形容词有效）：

```
优先级锚点（照此校准，不要普遍偏高）：
- 90-100：身份/家庭/价值观级，几乎不会变（"用户是 AI 开发者""原件永不删"）
- 70-89：重要但可演进（"当前主项目是 InfiniteTalk""NAS 部署 SGME"）
- 50-69：一次性事件、局部偏好（某次踩坑、某工具的选择）
- <50：丢弃
⚠️ 若你发现自己在给超过 1/3 的记忆打 80+，说明校准偏松，请整体下调。
```

最后那句"自我校准提醒"是我建议加的——直接对抗 LLM 的分数膨胀倾向。

### P1-2 提示词版本治理缺失（**直接阻塞 Gen3 评测**）

生产 `memories.prompt_version` 分布：

| prompt_version | 条数 |
|---|---|
| `l1_extraction:working-988b7bae` | 12,830 |
| `l1_extraction:working-61c644de` | 9,253 |
| `None`（版本管理落地前 / 降级直存） | 3,152 |
| `l1_extraction:working-12a5b26e` | 518 |
| `l1_extraction:working-04c9ed1a` | 69 |

**4 个不同的 working-sha 混在同一个记忆池里**，而 `prompts/manifest.yaml` 显示
**5 个 stage 全部 `active: '@working'`**，`prompts/versions/` 目录下**只有 2026-08-05 的 v001**。

即：**26 天里提示词至少改了 4 次，一次钉版都没打过。**

为什么这件事现在变严重：Gen3 进化方案阶段一要建评测基线，铁律是
「检索改动必须跑 A/B 回归」。但**提示词本身在裸奔**——
基线跑出来是 `working-988b7bae` 的结果，改天提示词一变，基线就失效了，
且无法回答"这次数字变化是提示词改的还是检索改的"。

**建议**：把「提示词改动 → 打钉版」设为流程硬约束（架构 §27 已有机制，只是没执行）：
每次改 `prompts/*.txt` 后跑 `publish` 打 v00N，需要对比时走 `ab` 分流
（`manifest.yaml` 的 `ab.enabled` 字段已就绪，一次都没用过）。

### P1-3 输出校验缺口

| 现象 | 证据 | 根因 |
|---|---|---|
| 4 条记忆打了 **4 个**维度（提示词规定最多 3） | `DIM_per_mem: [(1,6428),(2,17139),(3,2253),(4,4)]` | `_validate_item` 只校验非空，不校验上限 |
| 2 条 `memory_type='status'`（白名单只有 persona/episodic/instruction） | `MEMTYPE` 含 `('status', 2)` | 走了未过校验的路径（早期数据或 merge 分支） |

数量很小（4 / 2 条），属"脏但不致命"。修法：
`_validate_item` 补 `dims[:3]` 截断 + `memory_type` 兜底逻辑覆盖全路径。

## 四、P2：成本与健壮性

### P2-1 英文/混排语料适配

已在《v0.2 审查意见》B2 详述（检索侧停用词/分词缺陷）。提示词侧的对应问题是：
五套提示词全中文，维度清单也只给中文 `display_name` + 中文 `boundaries` 描述。
处理英文会话时，模型要把英文事实映射到中文维度语义，打标准确率无保障。

**注意**：这一项与 LoCoMo 评测强绑定，但**修它的收益不限于评测**——
用户日常会话里大量夹杂英文术语（模型名、框架名、代码），中文提示词对混排内容的
维度打标同样受影响。建议与 T-127 合并处理。

### P2-2 `l1_conflict` skip 率缺乏质量监控

生产近 60 run 的 action 分布：
`store 190 / skip 102 / update 101 / merge 98` → **skip 占 20.8%**。

即每 5 条新记忆有 1 条被判"与候选相比无增量"。这个数字本身**无法判断好坏**：
候选池是"向量 Top-50 ∪ 维度 Top-50"，重复记忆多 → skip 20.8% 可能完全合理；
也可能误杀了大量有价值的增量更新。

**难点**：被 skip 的新记忆不入库，**事后无法追溯**（`refine_runs` 只记 action_counts 计数，无明细）。

**建议**：① 加 skip 率监控（按日/按维度看趋势，突增即告警）；
② 若要看质量，需临时开采样日志（记录被 skip 的 content + 命中的候选 id），
跑一批人工抽检后再决定是否调提示词的 skip 判定尺度。

## 六、与《记忆系统进化方案 v0.2 / Gen3》的关系

> 结论：**不冲突，但存在两处硬依赖与一处同文件撞车，必须先排序再动手。**

### 6.1 硬依赖一：P0-1 必须排在评测基线之前

进化方案铁律：「阶段二任何检索改动，**必须**在阶段一评测基线上跑 A/B」。
但 P0-1 停用维度**本身就是一次提炼/检索侧的重大改动**——
`l15._build_prescreened_candidates` 按**维度**预筛候选（候选 = 向量 Top-K ∪ 维度 Top-N），
停用 projects 后，新记忆不再带该维度 → **候选池组成直接变化**。

这就卡成一个鸡生蛋：

| 顺序 | 问题 |
|---|---|
| 先建基线 → 再修维度 | 基线建在即将废弃的维度集上；修完后候选池巨变 → **基线作废，白跑 3–6 小时** |
| 先修维度 → 再建基线 | 形式上违反"改动前先有基线"，但基线才可信 |

**裁决建议**：把 P0-1 定性为「**基线前置的地基修复**」而非"检索改动"，
在基线建立**之前**完成；并在基线文档里钉死
「基线版本 = 停用后的维度集 + 钉版提示词 sha」，让基线可复现。

### 6.2 硬依赖二：T2-1a 结构边受维度停用影响

T2-1a 的两条边来源中，`scene_memories` 共现依赖 L2 场景聚合结果。
停用维度 → 新记忆维度分布变化 → 场景聚合输入变化 → 场景结构变化 →
**共现边 backfill 结果变化**。故 T2-1a 的 backfill 应排在 P0-1 之后。

### 6.3 撞车点：四五处改动同时瞄准 `prompts/l1_extraction.txt`
