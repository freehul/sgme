## 二、逻辑错误

### L1（P0）归档记忆触发外键崩溃 —— `AGENTS.md` 已列教训，至今未修

**现象**（实证复现，非推断）：

```
[A] 注入统计写入: True
[A] archive_memory 失败 -> IntegrityError FOREIGN KEY constraint failed
```

复现脚本：建 memory `m1` → `memory_stats_dao.record_inject(mem,'m1')` → `memory_dao.archive_memory(mem,'m1',superseded_by='m2')` → 抛 `sqlite3.IntegrityError`。

**根因**：

- `db.py:162` DDL：`memory_stats.memory_id TEXT PRIMARY KEY REFERENCES memories(memory_id)`，且 `db.py:246` 全局 `PRAGMA foreign_keys=ON`。
- `memory_dao.py:331-334` 归档时依次清理 `memory_tags` / `memory_sources` / `memory_vectors`，**唯独漏了 `memory_stats`**，随后 `DELETE FROM memories` 撞 FK。
- 讽刺的是作者当时是有意识的——`memory_dao.py:333` 留有注释「向量是派生数据，随记忆归档删除（memory_vectors **有 FK 到 memories，必须先删**）」。`memory_stats` 是 v0.7 后加的表，加表时**没有回头补这条清理链**。

**影响**：

- 触发路径：`engine/l15.py:291` 与 `l15.py:333`（Supersession 裁决）。**一旦 D4 被修好（record_inject 接线上线），L1.5 冲突裁决会在归档旧记忆时直接抛异常**——整批提炼失败回滚。
- 当前之所以线上没炸，纯粹是因为 D4 那个 bug（`record_inject` 从未被调用）**恰好掩盖了本 bug**。两个缺陷互相遮蔽，**修任何一个都会引爆另一个**。这正是 `AGENTS.md`「mock 测试全绿 ≠ 真实链路可用」里「归档 FK」那条教训的原文场景。

**修复建议**：

```python
# memory_dao.py:334 之前补一行
conn.execute("DELETE FROM memory_stats WHERE memory_id=?", (memory_id,))
```

配套：新增**真实 DB**回归测试 `test_archive_with_stats_row`（禁止 mock 连接），断言 `record_inject` 后 `archive_memory` 返回 True。建议同时在 `db.py` DDL 侧评估给 `memory_stats.memory_id` 加 `ON DELETE CASCADE`，把这类「加表忘补清理」的系统性风险从代码约定降级为 schema 约束。

### L2（P1）被停用的维度在服务重启后自动复活

**现象**（实证复现）：

```
停用 status 后 active 数 = 14 | status.active = 0
--- 模拟服务重启：再次 load_config + import_registry ---
重启后 status.active = 1   <-- 期望 0
```

**根因**：

- `server/app.py:412` 每次启动执行 `memory_dao.import_registry(mem_conn, cfg["dimensions"], cfg["aliases"])`。
- `memory_dao.upsert_dimension`（`memory_dao.py:36-51`）的 `ON CONFLICT DO UPDATE` 子句里**硬编码 `active=1`**。
- 于是任何通过 `PUT /v1/admin/registry/dimensions/{id} {active:false}` 停用的**内置**维度，下次重启被 YAML 无条件重新激活。

**影响**：直接推翻 `routes_registry.py:6` 的设计声明「停用（active=false）而非删除——历史记忆的维度标签保留可溯源」。管理员的停用操作**只在本次进程生命周期内有效**，重启即失效且无任何告警。对于「先停用一个噪音维度观察效果」这类运维动作，会得到完全错误的观测结论。

**修复建议**：`upsert_dimension` 的 `ON CONFLICT` 分支**移除 `active=1`**（保留 DB 现值）；`active` 只由 `update_dimension_fields` 显式改写。若确需 YAML 强制复位，另开 `--force-registry-reset` 显式开关，不能作为默认启动行为。

### L3（P1）运行时新增的维度重启后不进 L1 提示词；已停用维度反而仍在提示词里

**现象**（实证复现，同一脚本）：

```
新增 finance 后 active 数 = 15
--- 模拟服务重启 ---
重启后 DB active 数 = 16
重启后 cfg[dimensions] 条数(来自YAML) = 15
cfg 中是否含 finance = False          <-- 新维度不进提示词
cfg 中是否含已停用的 status = True     <-- 停用维度仍进提示词
```

**根因**：**双源真相（two sources of truth）未收敛**。

- 写路径：`POST /v1/admin/registry/dimensions` → 写 DB `dimension_registry`，**不回写 `registry/dimensions.yaml`**。
- 读路径：`config.py:load_config()` 从 **YAML** 组装 `cfg["dimensions"]`，而 `engine/l1.py:405 _render_l1_text` 的 `{{dimensions}}` 清单正是从 `cfg["dimensions"]` 生成。
- `routes_registry.py:79 refresh_dimensions()` 确实会在写库后把 `cfg["dimensions"]` 刷成 DB 值——但那只在**当前进程内存里**。`server/app.py:402-412` 启动序列是 `load_config()`（YAML）→ `import_registry()`（YAML→DB），**从不反向从 DB 刷新 cfg**。

于是重启后两个方向同时失真：

1. 自定义维度 `finance` 留在 DB 里（`active=1`，计数从 15 变 16），但**不在提示词清单中** → LLM 永远不会产出该维度 → 该维度事实上是个僵尸行。
2. 已停用的 `status` 因 L2 被复活成 `active=1`，且本来就在 YAML 里 → **照常进提示词**。

`routes_registry.py:80-84` 的注释自称修复了「#33 启动快照缺口」，但它只补上了「进程内」这一半，**跨重启的那一半缺口仍然敞着**。

**影响**：契约与代码注释共同承诺的「用户 UI / SCSM 经此接口**动态新增维度**，无需 schema 迁移」在重启后失效。这是个**静默失效**——无日志、无告警，运维只会发现「新维度加了但一条记忆都没打上」。

**修复建议**（二选一，不要都做）：

- **方案 A（推荐，最小改动）**：`server/app.py:412` `import_registry` 之后立刻追加 `cfg["dimensions"] = memory_dao.list_dimensions(mem_conn, active_only=True)`，即复用 `refresh_dimensions`。**确立 DB 为唯一运行时真相，YAML 降级为初始种子（seed）**。同时修 L2（否则 DB 里的 active 会被 YAML 冲掉）。
- **方案 B**：注册表写接口同步回写 YAML，YAML 保持唯一真相。但涉及并发写文件与注释丢失，成本高于 A。

选定后**必须同步修订** `SGME-数据模型设计-v0.1.md` 与 `registry/dimensions.yaml` 头部注释，明确「YAML = 种子 / DB = 运行时真相」的边界。

### L4（P1）TTL 过滤用字符串比较，`T` 分隔符导致每条 TTL 被系统性延长最多 1 天

**现象**（实证复现）：

```
now       = 2026-08-08 09:34:46
now-7days = 2026-08-01 09:34:46
'2026-08-01T00:00:01Z'     > now-7d ?  -> 1    <-- 错，已过期 7 天 9.5 小时，却判为未过期
'2026-08-01 00:00:01'      > now-7d ?  -> 0    <-- 对照组：换成空格分隔就正确了
'2026-08-01T23:59:59Z'     > now-7d ?  -> 1
```

**根因**：

- 落库格式：`_now_iso()` 产出 **ISO 8601 带 `T` 与 `Z`** 的 `2026-08-01T00:00:01Z`。
- 比较基准：`datetime('now','-7 days')` 是 SQLite 内建格式，**空格分隔无 Z**：`2026-08-01 09:34:46`。
- SQLite 对 TEXT 做**逐字节字典序**比较。日期部分相同后，比到第 11 字节：`'T'`(0x54) **>** `' '`(0x20)。
- 结论：**只要 `updated_at` 落在临界日当天，无论几点，一律判为「未过期」**。误差不是 9 小时，而是「向上取整到整天」，最坏 +23:59:59。

**影响**：

- 铁律 #4 的 TTL 语义（status=7天）实际执行为「7 天 + 至多 1 天」。
- `status` 维度 TTL 只有 7 天，多留 1 天 = **14% 的相对误差**，注入画像里会混进本该淘汰的过期状态。
- 该缺陷**同时存在于设计文档**（`SGME-数据模型设计-v0.1.md` L192 就是这条 SQL），所以属于「设计层错误」而非「实现走样」。

**修复建议**（按推荐度排序）：

1. **两侧都归一化**（推荐）：
   ```sql
   AND (m.ttl_days IS NULL
        OR strftime('%Y-%m-%dT%H:%M:%SZ', m.updated_at) >
           strftime('%Y-%m-%dT%H:%M:%SZ', 'now', '-'||m.ttl_days||' days'))
   ```
   或更简洁地用 `julianday(m.updated_at) > julianday('now') - m.ttl_days`（SQLite 的 `julianday` 能正确解析带 `T`/`Z` 的 ISO 串）。
2. **先改文档**：`SGME-数据模型设计-v0.1.md` L192 的示例 SQL 必须先订正，否则这条错误会被下一个实现者原样复制。
3. 补边界单测：构造 `updated_at = now - ttl_days - 1秒` / `- 1小时` / `- 23小时`，断言全部判为过期。

### L5（P1）L1.5 候选池对全池硬截断，且截断前未排序 → 高价值旧记忆被静默丢弃

**现象**：`engine/l15.py:183-189`

```python
anomaly = len(candidates) > top_k          # top_k 默认 50
if anomaly:
    logger.warning("候选池 %d 条 > top_k=%d → 截断 + anomaly_warn", ...)
    candidates = candidates[:top_k]        # ← 对整池截断
```

紧接着 `l15.py:193-200` 的 `char_budget`（24000 字符）再截一刀。

**根因（两层）**：

1. **违反铁律 #7**：铁律要求「全量召回**不截断**」，仅在「**单条新记忆**的候选超预算」时才 top-k 截断。代码是对**整个候选池**一刀切到 50 条，与 spec 的语义完全不同。同函数 docstring（`l15.py:154`）还写着「全量召回，不截断」——**注释与紧邻 6 行后的代码直接冲突**。
2. **截断前没有排序**：`candidates[:top_k]` 直接取 `list_memories_by_dimension` 的返回序（默认 `updated_at DESC`）。按 `priority` 降序的排序**只发生在 `char_budget` 分支内部**（`l15.py:199`），也就是说：**如果池子是 60 条但总字符没超 24000，那 10 条被丢的候选是按「最旧」而非「最低优先级」挑出来的**。

**影响**：

- 记忆库超过 50 条同维度候选后（对长期使用的单用户引擎，这是**必然会到达**的状态），L1.5 只能看到最近 50 条。
- 与**较早入库的高优先级记忆**（例如 `values` / `identity` 这类静态高优先级事实）产生的冲突**检测不到** → 重复记忆入库、矛盾记忆共存，Supersession 形同虚设。
- 铁律 #7 的 `anomaly_warn` 虽然打了，但它标记的是「池子大」，而非「你丢了什么」——运维无法据此定位问题。

**修复建议**：

1. 短期止血：截断前先 `candidates.sort(key=lambda c: (c.get("priority",0) or 0), reverse=True)`，让 top_k 至少丢的是低优先级的。
2. 正解（对齐铁律 #7）：删除整池 top_k 截断；改为**按新记忆分组**——对每条新记忆单独取其维度候选，仅当**该条**候选超 batch_budget 时才 top-k 截断并打 `anomaly_warn`；候选按 `batch_budget` 分批，保证「同一新记忆只进一批」。
3. 同步处理 `l15.py:381-384` 那段「简化：所有新记忆作为一批」的注释——要么实现对齐 spec，要么把偏离作为**显式设计决策**写进 `AGENTS.md` 并修订铁律 #7 的措辞。不能让代码注释长期承认「我没按 spec 做」。
4. `l15.py:178-179` 顺带修 N+1，见 L7。

### L6（P2，潜在）`batch_budget` 默认 `prompt_overhead=0.8`，与配置 `0.08` 差 10 倍

**现象**：`llm/chain.py:72` 与 `:77` 两处默认值均为 `0.8`：

```python
rules = {"context": {"reserved_output": 4096, "prompt_overhead": 0.8}}   # :72
overhead = ctx.get("prompt_overhead", 0.8)                                # :77
```

而 `config/llm.yaml:39` 是 `prompt_overhead: 0.08   # 提示词开销比例（8%）`。

实测偏差：

| provider | context_window | 正确（0.08） | 兜底（0.8） | 缩水倍数 |
|---|---|---|---|---|
| lm-studio | 65536 | **56197** | 9011 | 6.2× |
| deepseek | 1048576 | **960593** | 205619 | 4.7× |

**根因**：0.8 是 0.08 的**小数点笔误**，且被复制到了两处。

**影响与触发条件**：

- 当前**未触发**：两个调用点（`l15.py:388`、`l2.py:261`）都传了 `llm_cfg.get("rules", {})`，而 llm.yaml 里 `context.prompt_overhead=0.08` 存在。
- **但第二处默认值是可触发的**：`llm_cfg.get("rules", {})` 返回的是 `{}` 时（rules 段缺失），`ctx = {}.get("context", {})` = `{}`，于是 `overhead` 取 `0.8`。也就是说**只要有人删掉或改名 llm.yaml 的 `context` 段，预算立刻缩水 6 倍**，且不会报错——只表现为「提炼变慢了、分批变多了」，极难定位。
- `l15.py:386` 还有一个硬编码 fallback `budget = 55360  # 默认 64K 链预算，实际应从 llm_cfg 读`，属同类隐患。

**修复建议**：把两处 `0.8` 改为 `0.08`；更好的做法是**去掉默认值**，`context` 段缺失时直接抛 `ValueError`（配置错误应当 fail fast，而不是静默用一个错误的魔数继续跑）。同时清理 `l15.py:386` 的硬编码 55360。

### L7（P2）`build_candidate_pool` N+1 查询，且同一行调用两次 `get_memory`

**现象**：`engine/l15.py:178-179`

```python
for c in candidates:
    c["tags"] = memory_dao.get_memory(mem_conn, c["memory_id"]).get("tags", []) \
                if memory_dao.get_memory(mem_conn, c["memory_id"]) else []
```

**根因**：三元表达式的条件分支与取值分支**各执行一次** `get_memory`。而上游 `list_memories_by_dimension` 的 `limit=10000`。

**影响**：最坏 10000 候选 × 2 = **20000 次额外查询**（每次 `get_memory` 内部还要再查 tags 表）。这是 L1.5 提炼耗时的一个隐性大头，也是当初不得不加 `top_k=50` 硬截断（L5）的**根本诱因之一**——性能问题被用「砍数据」而不是「改查询」来解决，结果引入了正确性问题。

**修复建议**：先把结果存变量（一次调用），治标；治本是给 `memory_dao` 增加 `batch_get_tags(conn, memory_ids) -> dict[str, list[str]]`，一条 `WHERE memory_id IN (...)` 批量取回。改完后 L5 的 top_k 截断就失去了性能上的借口，可以顺势按铁律 #7 改正。

## 三、潜在问题 / 风险

### R1（P1）Mock 测试掩盖真实缺陷 —— 系统性风险，非个案

`AGENTS.md` 已明确写下教训「mock 测试全绿 ≠ 真实链路可用」，但本次审计发现**该模式仍在复现**：

| 模块 | 测试覆盖 | 真实链路 |
|---|---|---|
| `validate_models` | **12 个单测**全绿 | **零生产调用点**（D3） |
| `record_inject` | 4 个单测全绿 | **零生产调用点**（D4） |
| `archive_memory` | 有测试 | 测试**从不先写 memory_stats 行**，故永远测不出 L1 的 FK 崩溃 |

**共性**：单测把「函数正确性」和「函数被正确接线」当成一回事。三者都是「实现完成 → 测试通过 → 任务勾掉」，但没人验证过调用方存在。

**建议**：
1. 引入**接线检查**：对声明为「唯一写入口」「拒绝启动」等具有系统语义的函数，加一条元测试断言其在 `sgme/`（非 `tests/`）内至少有一个调用点。这类测试写起来只需 10 行 grep，收益极高。
2. `archive_memory` 类涉及 FK 的用例，测试夹具必须**填满所有引用表**再执行删除，否则等于没测。

### R2（P1）三库快照非原子，跨库引用可能在备份中断裂

`backup/manager.py:66-79` 对每个库单独调用 `src_conn.backup(dst_conn)`。SQLite backup API 保证**单库**一致，但三次调用之间没有全局屏障。

**风险场景**：备份进行中恰好有一次 `refine_file` 提交——memory.db 已快照（不含新记忆），session.db 后快照（`raw_files.status` 已变 `refined`、`last_refined_seq` 已推进）。恢复后该文件被视为已提炼，但记忆不存在，**数据静默丢失且水位线自检（铁律 #11）也检测不出来**（因为 `refined_at` 是新的）。

**建议**：备份期间加一把进程级互斥锁，阻塞提炼调度（`batch_refine_task` / `refine_on_append`）；或按固定顺序 session.db → memory.db → wiki.db 快照，并在 `verify_integrity` 中增加跨库引用校验（抽样检查 `memory_sources.source_ref` 是否都能在 session.db 的 raw_files 中找到）。

### R3（P2）单一 SQLite 连接跨线程共享 + 手动 `BEGIN`，存在事务串扰

- `db.py:243` `check_same_thread=False`，`app.state.mem_conn` 是**全应用共享的单一连接**，FastAPI 同步端点跑在 threadpool 里。
- 同时代码中有 5 处显式 `conn.execute("BEGIN")`（`memory_dao.py:72/178/313`、`data/search/__init__.py:119/254`），每处结尾都 `conn.commit()`。
- **共享连接上的 `commit()` 是连接级的**：线程 A 的 `archive_memory` 提交时，会**连带提交**线程 B 尚未完成的中间写入；反之线程 A 的 `rollback()` 会**回滚掉** B 已经写好的数据。

单用户场景下并发极低，所以至今没出事，但这是**竞态而非不可能**——`batch_refine_task` 定时器与用户 HTTP 请求本来就在不同线程。

**建议**：中期改为 per-request 连接（或连接池 + `threading.local()`）。短期至少给写事务加一把全局 `threading.Lock`，把「单用户所以安全」的假设从注释里的口头承诺变成代码里的实际约束。

### R4（P2）注册表双源真相是 L2/L3 的共同根因，需架构级裁决

L2 与 L3 不是两个独立 bug，而是**同一个架构缺陷的两个症状**：YAML 与 DB 都自认为是维度注册表的真相。修复时若只打补丁（比如单独修 L2 的 `active=1`），L3 依然存在。必须先做架构裁决（DB 为准 / YAML 为准），再一次性改完读写两侧 + 文档。

### R5（P2）TTL 只做读过滤，记忆永不物理淘汰

TTL 仅出现在 `list_memories_by_dimension:398` 的查询条件里。全仓无任何按 TTL 归档/清理的定时任务（`engine/prune.py` 是 **L0 消息剪枝**，与记忆 TTL 无关，名字容易误导）。

**后果**：过期记忆永久滞留 `memories` 表，持续参与：FTS5 索引、向量索引（`memory_vectors`）、L1.5 候选池 OR 召回（`include_expired=True`，`l15.py:177`）。库体积与 L1.5 耗时**单调增长**，且会加剧 L5 的截断丢失问题。

**建议**：明确 TTL 语义——是「不注入但保留可溯源」（当前实现）还是「到期归档」。若是前者，应在设计文档中写明并规划独立的冷归档策略；若是后者，需新增定时任务。**这一条建议先改文档**，因为当前文档对此完全沉默。

### R6（P2）LLM 降级链 401 静默降级的历史事故防线仍不完整

`config.py:31-37` 记录了 2026-08-07 事故：nssm 覆盖式 set 冲掉 `DEEPSEEK_API_KEY` → 提炼链 401 **静默降级**到本地 9B 模型，提炼质量断崖但无人察觉。当前已用 `load_env_file()` + `setdefault` 缓解，`engine/health.py` 也补了带 Bearer 的 `/models` ping。

**残余风险**：降级本身仍是静默的——`call_with_fallback` 从 deepseek 掉到 lm-studio 只写日志，不产生 signal 事件、不影响 `/v1/health` 的整体状态。运维仍然要靠翻日志才能发现「今天的记忆都是 9B 提炼的」。

**建议**：主节点失败触发降级时，写一条 `signal_events`（type=`llm_degraded`），并在 `/v1/health` 与 `stats` 中暴露「最近 24h 各节点承担的提炼批次占比」。这是低成本高价值的可观测性补强。

### R7（P2）`eval/` 与生产数据的隔离仅靠约定

评测设计文档承诺「绝不碰生产 `data/memory.db`」，隔离方式是 runner 传入 `eval/tmp/` 目录。但 `db.py:266` 的 `connect_memory(data_dir=None)` **默认回落到 `config.DATA_DIR`（生产目录）**——任何一处漏传 `data_dir` 的新代码都会直接写生产库。目前 `eval/` 有 12 个模块、`runner.py` 达 33KB，人工保证难以持久。

**建议**：加环境变量 `SGME_DATA_DIR` 覆盖，评测入口统一设置；或在 `connect_memory` 中检测 `SGME_EVAL_MODE=1` 时拒绝落到生产目录。

### R8（P2）`eval/` 目录游离于分层铁律之外

`eval/` 与 `sgme/` 并列（设计文档 §0 明确如此），但它直接 import `sgme.engine.l15` 等内部模块。这意味着**引擎层的任何签名变更都会静默破坏评测**，而评测又是质量防线本身。当前 `eval/runner.py` 33KB 且无文档（D7），维护风险随体量增长。

**建议**：为 `eval/` 明确定义「只允许经由 `sgme.operations` 与 `sgme.engine` 的公开函数接入」的边界，并把 D7 的文件清单补齐。
