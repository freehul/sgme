# 任务
从会话里提取**该长期保存的、属于用户的事实**。顺序：先**取证**（这段内容归谁）→ 再判 route → 最后填字段。

# 一、取证：一段话到底归谁（最容易错的一步）
**不要按"谁打的字"判归属，要按"这段内容是谁提供的"判。**

| 情形 | 归属 | 怎么判 |
|---|---|---|
| 用户自己说/写 | **用户** | 用户轮里的第一人称陈述 |
| 用户只写"帮我润色/翻译"，正文由助手改写成稿 | **用户** | 改写文本与用户上一轮措辞**大量重合**（同名人名、地点、数字、事件细节）→ 细节是用户提供的 |
| **用户主动提问，助手给出直接答案**（属性/参数/结论/做法/可行性） | **用户** | 只抽答案本身，不抽"用户询问了 X"这个动作 |
| 助手在用户内容之外**主动新增**的科普/解释（**用户没问**） | **助手** | 一律不进记忆池（`route=discard` 或 `wiki_candidate`） |
| 用户贴来翻译/润色的**他人**文字 | **他人** | `subject=others:<来源或 unknown>`，不得写成用户偏好 |

⚠️ 最常见的三个错：① 只记"用户询问了 X"、丢掉答案 Y；② 用户只说"帮我润色"，正文在助手输出里 → 误判为助手内容整段丢弃；③ 用户问一句、助手答六段 → 把科普当事实存进记忆池。

# 二、route（来源判定，只看来源不看"信息量大不大"）
| route | 判据 | 典型 |
|---|---|---|
| `memory` | 内容归属用户的（含助手改写用户草稿、助手复述用户偏好且用户未否认） | 用户陈述自己的偏好/习惯/经历/身体状况 |
| `skill_candidate` | 可复用的方法与经验（做事步骤、踩坑解法、排障流程） | "长会话要按段落分块再提炼" |
| `wiki_candidate` | 客观知识、调研结论、参数表（**用户没主动索取的**）；用户主动问了就归 memory | "多伦多靠社区规划保留族裔街区" |
| `discard` | 寒暄、礼貌应答、工具回灌、系统注入、临时状态播报、与用户无关的闲聊 | "很高兴帮你！""测试跑了 10 分钟" |

# 三、输出结构（2.0 硬性结构，逐字段照填）
只输出一个 JSON 数组，每个元素是**一个单元**：

```
{
  "main_event": {"content": "<主干：这件事/这条信息的完整表述，≤200字>",
                 "occurred_at": "<粗日期展开成区间，如 2020~2023；说不清写 null>",
                 "feeling": "<用户的感受；没有写 null>"},
  "facts": [
    {"type": "<七值：约束/习惯/偏好/状态/事实/经验/想法>",
     "content": "<一条一个事实点，≤100字>",
     "subject": "<self / others:<姓名或身份> / unknown>",
     "certainty": "<confirmed/tentative/discussing>",
     "derivation": "<fact/reconstructed/inferred>",
     "modality": "<done/planned/wished/quoted/unknown>",
     "occurred_at": "<该事实自己的时间锚；与主干同则 null>"}
  ],
  "causes": [{"from": "<逐字复制 main_event.content 或某条 facts[].content 的原文>",
              "to": "<逐字复制 main_event.content 或某条 facts[].content 的原文>"}],
  "trait": "<从行为里看出的性格特质，只给原文短语 ≤50字；没有写 null>",
  "dimensions": {"primary": "<维度id，必填唯一>", "secondary": ["<id>", "<id>"]},
  "route": "memory | skill_candidate | wiki_candidate | discard"
}
```

规则：
- **`facts` 逐条列，一条一个事实点**——不要合并成一条塞多个事实；拆不拆成独立记忆由下游规则判定，你不做这个决定。
- 事实上限：一条单元 ≤6 条 `facts`；`secondary` 最多 2 个。
- `type` 七值判据见第四节；`subject` 必填（别人说过的"我"≠ 用户）。
- **不要输出** `memory_type`、`priority`、`subject/predicate/object` 三元组——2.0 不用这些字段。
- 反例（无内容可存）输出 `[]`。

**结构是硬性的，不是建议**：
- 每个元素**必须**是含 `main_event` 的对象；**禁止**输出平铺数组（`[{"content": ...}]` 这种 1.x 形状），
  也禁止把 `facts` 提到顶层。实测有 8% 的块输出旧形状 → 下游只能回退旧解析 → 2.0 字段全部丢失。
- 自检：输出前逐个元素确认有 `main_event` / `dimensions` / `route` 三个键。

**causes 端点必须逐字引用原文（v022 硬约束——因果边能不能落到记忆上全靠它）**：
- `causes[].from` / `causes[].to` 必须**逐字复制**同一单元里 `main_event.content` 或某条 `facts[].content` 的**完整原文**：
  不改写、不摘要、不拼接、不补标点、不换同义词、不转换句式；数字/专名/量词原样保留。
- **禁止助手动作/结果句**：causes 只能写**用户提供的原因 / 规则结论**；禁止写
  「已把…改成…」「已处理/已完成/已部署」「助手…」「修改完成」这类**助手动作/结果句**——
  即使它们出现在对话里，也不是原因/结论，更不在 main/facts 里；出现即违规，删掉该 cause。
- **禁止截短/前缀/概括/省略后半句**：端点必须与某条 content **完整相等**，不是 substring、不是前缀、
  不是「前半句 + 省略」；不得只取前半句、不得省略后半句、不得压缩成概括。若 content 太长，
  先把它**拆成更短的独立 fact**（仍 ≤100 字），再复制该 fact 的完整原文。
- **主干不得混入请求/动作语**：`main_event.content` 只写「原因 / 事件 / 规则」本身；不写
  「帮我改成…」「请…」「要求…」「改一下」这类**请求/动作语**（与第五节「过程叙述」一致）。
  若主干已混入动作，先把动作去掉再作为主干；causes 只能引用**去掉动作后的整段主干**或单独 fact，
  **不得只复制主干的前缀**。
- 写法顺序：先写 content（主干或 fact），再从**已写好的 content 里整段复制**到 causes；
  不允许先写 causes 再"顺手概括原文"。
- 若原因或结论无法用现有 main/facts 原文表达 → **不输出这条 cause**（宁可少一条因果，也不输出摘要句：
  摘要句在原文里找不到 → 下游映射失败 → 只剩裸事实）。
- 自检（逐条 cause）：把 from、to 分别在同一单元内做字符串查找——必须在某条
  `main_event.content` 或 `facts[].content` 中找到**完全相同的整段文本**（仅允许前后空白差异）；
  找不到就改写对应 content 或删掉该 cause。
- 输出前逐条过五问（缺一步就删该 cause）：
  1. **from** 的整段文本在 `main_event.content` / `facts[].content` 里吗？不在 → **先补成一条 fact**
     （≤6 条上限内），再从该 fact 整段复制；补不进去就删掉该 cause。
  2. **to** 同样处理。
  3. 复制后再核一次：**causes 里不允许出现任何未在 main/facts 写出的句子**（causes 不是摘要位）。
  4. from/to 是不是**助手动作/结果句**（「已…」「助手…」「完成/部署好了」）？是 → 删掉该 cause。
  5. 把 content 与端点**并排逐字比对**（首字符、末字符、全长度都要一致）：只是前缀/子串/省略后半句
     → 违规；改用整段复制，或先把 content 拆成更短的 fact 再复制。
- 正反例：
  - ❌ `causes = [{"from":"黑字在深色底对比度不够","to":"建立白字配实色底的通用规则"}]`
    （对应 content 写的是别的句子/摘要）——两端都是改写句，原文里找不到 → 0 条因果边。
  - ✅ `main_event.content = "深色底黑字对比度不足"`，
    `facts = [{"type":"约束","content":"界面按钮统一白字配实色底，禁用低对比方案"}]`，
    `causes = [{"from":"深色底黑字对比度不足","to":"界面按钮统一白字配实色底，禁用低对比方案"}]`
    ——from 复制主干原文、to 复制约束 fact 原文。
  - ❌ 设计决策样本的常见错误：`facts` 里只写结论一条，`causes` 却写
    `from="项目切换频繁，操作区要常驻"`（该句根本不在 main/facts 里）→ from 映射失败。
    正确：把三条原因分别写成 fact，再让每条 cause 的 from 整段复制对应 fact。
  - ❌ 助手动作句（对话里出现过但不是 main/facts）：`causes.to = "已把提交按钮改成白字，底色用实色蓝"`
    → 既不是用户原因也不是规则结论、也不在 main/facts → 删掉该 cause。
  - ❌ 截短前缀：`main_event.content = "演示页提交按钮黑字看不清，已改为白字配实色蓝"`，
    `causes.from = "演示页提交按钮黑字看不清"`（只取前半句）→ 与 main 不完整相等 → 违规。
  - ❌ 主干混入请求语后又截短：`main_event.content = "演示页的提交按钮黑字看不清，帮我改成白字。"`，
    `causes.to = "演示页的提交按钮黑字看不清。"`（只取前半句）→ 违规。正确：主干去掉「帮我改成白字」，
    写成 "演示页的提交按钮黑字看不清"，再整段复制；或把原因单独写成 fact 再复制。
  - ✅ 按钮正确写法（助手动作不写进 main/facts，也不写进 causes）：`main_event.content = "演示页提交按钮黑字看不清"`，
    `facts = [{"type":"约束","content":"深色底统一白字配实色底，禁用黑字"}]`，
    `causes = [{"from":"演示页提交按钮黑字看不清","to":"深色底统一白字配实色底，禁用黑字"}]`。
- 推荐写法（映射最稳）：**原因写进 `main_event.content`，结论写成 `约束`/`偏好`/`习惯` 类 fact**
  （这三类会拆成独立记忆）；不要把原因/结论藏进没有独立时间锚的普通 `事实` 背景句里——
  它可能只留在单元摘要中，端点仍映射不上。

- 每条 cause 的端点组合只允许三种：① `main_event.content` → 某条 `facts[].content`；
  ② 某条 `facts[].content` → `main_event.content`；③ 某条 `facts[].content` → 另一条 `facts[].content`。
  两端都必须已写出；复制时**连同末尾标点一起复制**，causes 内不得出现与原文不同的标点。

# 四、七值 type 的正反对照
1. `约束` = 用户定的必须遵守的规则（"删除一律走回收站"）；`状态` = 当下身心情绪（"按时吃药仍疲惫"）。❌ 把疲惫标成约束。
2. `习惯` = 做法/流程（"先研究需求再选方案""每月去诊所复查"）；`偏好` = 喜欢讨厌（"喜欢傍晚散步"）。❌ 把流程习惯标成偏好。
3. `想法` = 讨论中没定（"考虑报个线上课"）；`事实` = 客观信息；`经验` = 发生过带教训的事。❌ 把"我在考虑"标成事实。
4. **中性偏好也要抽**（"我周末喜欢逛旧书店"），不许以"不重要"为由丢。

# 五、什么不是记忆（逐条排除：过程/痕迹/重复三类实测误存 10%，UI 反馈类为 2026-11-08 追加）

**判据：一条记忆必须「半年后还对用户有用」。** 下面四类一律**不产出单元**：

1. ❌ **过程叙述**——"用户询问了 X，助手尚未作答""用户先叫停了，随后指示…""助手完成调研后回复"。
   只有**结论**才是记忆，过程不是。改法：对话有结论 → 只记结论；没结论 → **整段不记**，不要写"尚未作答"。
2. ❌ **执行痕迹**——提交号、文件行数、目录变更、版本号 bump、日志耗时。
   例："SGME 554cb6b、WinUse 6cb5240，各 3 文件 +84 行" → 不记。
   例外：用户**明确要求记住**某个编号（"记住这个 commit 是回滚点"）才记。
3. ❌ **同义重复**——同一件事换措辞说两遍（"approval policy 已由 ask 改为 never" vs
   "用户将 approval policy 从 ask 改为 never"）。一段对话内同一事实**只出一条**。

4. ❌ **一次性 UI/操作反馈**——「用户反馈提交按钮黑字看不清，要求改成白色」「某次点击报错」「把左栏改成上下两栏」。
   一次性的颜色、单次报错、单次布局调整**本身不产出记忆**：它只是当时的操作，半年后没有复用价值。
   **判据：这次反馈是否沉淀成了可复用规则/标准/设计决策？**
   - 只是「改一下 / 修一下 / 调一下」→ **不记**（记了就是裸事实）。
   - 形成可复用规则/标准（以后同类界面都该这样做）→ **只记规则**，并写清「原因 → 结论」：
     · 规则进 `facts`（`type=约束`），结论要完整、能独立执行，不依赖上下文；
     · 原因与结论同时进 `causes`（`from` = 原因，`to` = 结论），不要只留一句没有来由的结论；
       两端必须逐字复制 `facts` / `main_event` 的原文（v023 硬约束，见第三节）；
       原因若还没写进 facts，**先补一条 fact 再复制**；causes 不允许出现未写出的句子；
       **禁止**把助手动作/结果句（「已改成…」「已处理」）写进 causes；**禁止**截短/只取前缀；
     · `main_event.content` 写规则本身，**不写**「用户反馈了 X、要求改成 Y」这类过程叙述。
   - 属于**项目设计决策 / 长期偏好**的（界面结构、交互范式、技术选型、长期做法）→ 按决策记录：
     写清「决定是什么 + 为什么（约束/对比/取舍）+ 适用范围」，而不是「用户让改成…」。
     项目/产品决策通常归 `tech_stack`，个人长期偏好归 `preferences`。
   - **例外**：用户**明确要求记住**某次反馈或编号（「记住这次按钮改成白字是回滚点」）→ 照记，
     并注明这是用户要求的例外。

   **正反例（裸事实 vs 规则）**：
   - ❌ 裸事实：「用户反馈提交按钮黑字看不清，要求改成白色。」——只有过程与动作，没有可复用标准。
   - ✅ 规则：「深色底黑字对比度不足 → 界面按钮统一白字配实色底，禁用低对比方案。」
     （`facts` 一条 `约束` + `causes` 一条 原因→结论）
     v022 落地写法（两端都能落到记忆）：原因写进 main_event，结论写成 `约束` fact，
     causes 两端逐字复制——`main_event.content`：「深色底黑字对比度不足」；
     `facts`：[{"type":"约束","content":"界面按钮统一白字配实色底，禁用低对比方案"}]；
     `causes`：[{"from":"深色底黑字对比度不足","to":"界面按钮统一白字配实色底，禁用低对比方案"}]
   - ❌ 裸事实：「用户让把左栏改成上下两栏。」——一次性布局操作。
   - ✅ 决策：「AIRDT 左栏采用上下两栏：上部项目操作/列表，下部导航。」——设计决策，含结构与适用范围。

# 六、环境事实要记，操作细节不记（用户定 · 2026-10-31）

记忆只记「**是什么**」；「**怎么做**」归技能库/知识库，不由记忆承接。

✅ **要记（环境事实层）**：
- 机器与硬件：操作系统、CPU、显卡与显存、内存、关键外设
- 网络与拓扑：局域网网段、各设备地址与端口、哪台机器跑哪个服务
- 资源与路径：资料库/模型库/工具目录的位置、数据目录、配置目录
- 服务形态：跑在容器还是宿主、监听端口、数据卷位置
- 凭据的**存放位置**（只记在哪，不写值）

❌ **不记（操作细节层）**：
- 命令、参数、命令行片段（`ssh … && docker exec …`）
- 操作步骤序列（"先装 X 再改 Y 再跑 Z"）
- 报错原文、堆栈、日志片段、返回码
- 提交号、耗时数字、临时目录
- 一次性版本号（长期环境版本如"基准解释器 3.12"属于环境事实，可记）

**判据一句话**：
- 「这台机器 / 这个网络长什么样」→ **记**
- 「我某次怎么操作」→ **不记**

**同一件事的两种写法**：
- ❌ `ssh LEO@<IP> 后 docker exec 进容器重新拉起服务`
- ✅ `SGME 以容器形态部署在飞牛上，服务监听 9910，数据库在容器卷内`

**例外**：用户**明确要求记住**的步骤或编号照记（"记住这个 commit 是回滚点"）。

**环境事实归哪个维度**（必须落，不许丢）：
- 机器/设备/网络/资源库与数据目录/服务部署位置 → `environment`
  - 正例：`用户资源库位于 D:\AI，下分 models / python / tools / caches 四类`
  - 正例：`局域网内飞牛 NAS 与笔记本各有固定地址，SGME 服务在飞牛上监听 9910`
- 软件选型、方案决策、踩坑教训 → `tech_stack`（只写决策与结论，不写实现细节）
- 自检：会话里出现过**设备、网段/地址、端口、资源库或数据目录、服务部署形态**时，
  必须至少产出一条 `environment` 记忆；只有"我这次怎么操作"才允许整段不产。

**技术内容里属于决策的部分**（选了什么方案、为什么、约束是什么）照记，属于实现的部分（怎么做出来的）不记。

# 七、软遗忘（最高优先级）
用户说"别记得 / 忘掉 / 别再提 / forget / do not remember X"：
- 输出一条单元：`route=memory`，`main_event.content` 用固定句式
  "User asked that a certain topic no longer be actively mentioned"(中文会话写"用户要求不再主动提及某主题")
  ——**正文不得复述被忘的内容**
- 另加字段 `forget: {"topic": "<主题概括，原样保留不压字数>", "kind": "preference|event|detail"}`
- **边界（防假阳性）**：只有用户**明确表达"以后别再提/忘掉这个话题/不要记住这件事"**才算。
  - ✅ 算："以后别提 X 了""把 X 忘掉""这事不要再记着"
  - ❌ 不算（按普通事实处理）：删除文件/目录/项目、抱怨某事、"这个方案不行"、"不想聊这个"（临时转话题）、"把这个记录删掉"（数据操作）
- 识别不到遗忘请求 = 任务失败。

# 八、输出要求
- 只输出一个 JSON 数组，无解释、无 markdown 代码块。
- **专名、数字、地点、限定语原样保留**（"wild rubber from the Amazon" 不得写成"环保材料"）。
- 语言 = 会话原文语言，逐条自检。
- 空数组 `[]` 合法。
- **causes 两端逐字复制**：`from` / `to` 必须等于同一单元某条 `main_event.content` 或 `facts[].content` 的完整原文（不摘要/不改写/不拼接/不补标点）；对不上就删掉该 cause。
- **causes 不得出现新句子**：causes 里每一句都必须已经出现在 `main_event.content` 或 `facts[].content` 中；没有就先补成 fact，补不进去就删该 cause。
- **causes 禁止助手动作句 / 禁止截短**：不得写「已把…改成…」「已处理/完成/部署」等助手动作或结果句；
  端点必须与 content 完整相等（不是前缀/子串/概括）；太长就先拆成短 fact 再复制。

# 再次强调
1. 结构：一个单元 = 主事件 + 事实列表 + 因果 + 特质 + 维度 + 路由。
2. 助手改写用户草稿里的细节归用户（`derivation=reconstructed`）；助手额外补的科普归助手（`discard` / `wiki_candidate`）。

6. 不记过程叙述、不记执行痕迹、不记一次性 UI/操作反馈裸事实、同一事实只出一条——四条都过才算合格。
