# SGME 汇报规范 v1（跨宿主通用）

> 适用对象：所有接入 SGME 的 agent。触发场景：向用户输出结论、进度、方案、故障说明。
> 目标：换宿主、换模型，报告的结构与证据密度保持一致；渲染能力不同只影响呈现形式，不影响内容契约。
> 版本：v1（2026-11-07）。完整规范随 SGME onboarding 模板（SGME-ONBOARDING-v4）下发。

## 一、内容契约（五项，缺一不可）

1. **结论先行**：第一句就是判断/结果，不铺垫。
2. **关键数据**：数字必须实测；附来源（接口 / 文件 / 命令）。没测就写「未验证」。
3. **要点或依据**：列表呈现，≤7 条；每条一句话讲清因果。
4. **遗留风险 / 未验证项**：明确写出来，不藏。
5. **下一步**：给选项，不替用户做决定（除非用户已明确授权）。

> 特例：一句话就能答的问题不必套五项；但只要涉及状态、对比、故障、交付，五项必须齐。

## 二、渲染三档（按宿主能力选择，不混用）

| 档位 | 适用宿主 | 呈现方式 |
|---|---|---|
| R 富 UI | DSH（dsh-genui 插件） | `dsh-ui` 围栏：callout / table / list / steps；输出前先校验 |
| M Markdown | Claude Code / Codex / ZCode / Hermes / 豆包 / MiMo / WorkBuddy | 小标题 + 列表 + 粗体；表格 ≤4 列、单元格 ≤30 字 |
| P 纯文本 | 终端 / 短信 / 语音等无富文本通道 | 小标题 + 列表；不用表格语法，指标一行一个 |

**判定方法**：宿主能渲染 `dsh-ui` 围栏 → R；能渲染 Markdown 表格 → M；其余 → P。
不要向非 DSH 宿主发送 `dsh-ui` JSON（会显示原始文本）。

## 三、硬规则

- **数字必须实测**：没跑过的命令不许写「已通过」；失败三次先查官方文档，再升级方案。
- **推断与事实分开**：推断写「推断」，未验证写「未验证」。
- **方案没跑通不许说完成**；半成品要标注。
- **不擅自扩大范围**：改了什么、没改什么，分开写。
- **表格只放对比与指标**：叙述用列表；手机优先，中文单行 ≤40 字。
- **来源可追**：文件路径 / 接口 / 命令 / wiki page_id / 记忆 id，至少给一种。

## 四、反模式

- 只有结论、没有证据；
- 一张超宽表塞十几列；
- 把 `dsh-ui` 围栏发给非 DSH 宿主；
- 用「全部完成」「应该没问题」掩盖未验证；
- 交付时不写验证命令与实跑输出。

## 五、验收方法

同一组 3 个问题（一次进度汇报、一次方案对比、一次故障说明）在 R / M / P 三档各跑一次，检查五项是否齐全。
五项缺失任意一项即不合格；渲染形式不同不算不合格。

## 六、下发通道（2026-11-07 定）

- **onboarding 模板 v3**：`agent_onboarding().self_config.template` 含本规范摘要；已接入 agent 下次自检按版本标记回写身份文件。
- **在线文档**：`GET /v1/onboarding/docs/report-style.md`（免 Key）；`/v1/health` 的 `onboarding.report_style` 给出指针。
- **技能**：`report-format`（唯一权威；`output-conventions` / `structured-reply` 已并入并软删）。
- **不做** `/v1/inject` 固定段（2026-11-07 用户定）：所有接入 SGME 的 agent 本来就要取自己的 ID 并阅读 AI-INSTALL 文件，不额外占用注入预算。

## 七、与宿主差异的关系

- 内容契约（第一节）与硬规则（第三节）**所有宿主一致**；
- 渲染形式（第二节）按宿主能力降级，**允许不同**；
- 各宿主适配器在自己的说明里声明档位（R/M/P），不重复定义规范。
